## 2. Отклонения и риски (по убыванию значимости)

### R1. Батчинг: самописные `BatchProcessor` вместо TPL Dataflow (ориентир)
- EventLog: `IBlockTrackingReader → .Batch → WriteTo` на Dataflow с `BoundedCapacity`/
  `EnsureAtomicBatch`/`DegreeOfParallelism`. У нас: `Channel` + цикл + `SemaphoreSlim`-гейт.
- Текущая реализация протестирована (T5-семантика: ретраи, финальный drain, never-cancelled
  in-flight) и соответствует поведению по backpressure и пакетированию. Dataflow-версия
  проигрывает в durability-семантике (BatchBlock не даёт повторного пуска упавшего батча).
- **Рекомендация: оставить Channel-конвейер; задокументировать отклонение** (сделано здесь).
  Альтернатива (переписать на Dataflow) — дорого и регресс T5.

### R2. Нет HealthChecks (в AGENT.md §9 заявлены)
- Состояние RAS-сессий/кластеров недоступно оркестратору; проблема видна только из логов.
- **Рекомендация: добавить** минимальный `IHealthCheck`: статус последнего успешного
  цикла по каждому (server, cluster) + pipeline queue depth; `AddHealthChecks()` в Program.

### R3. Фиксированный интервал переподключения (5 c) без backoff/jitter
- При недоступном RAS N кластеров×M серверов лавинно долбят сервер каждые 5 c.
  LoadSim показал: сервер держит 50+ соединений, но на продакшн-мониторе с 10+ серверами
  это шум и лишний трафик.
- **Рекомендация: экспоненциальный backoff 1→2→5→10→30→60 c + jitter (±20%), сброс на успех.**

### R4. Учётные данные в открытом виде
- `appsettings.json`: пароли RAS-админов/кластеров и ClickHouse лежат в файле конфигурации
  (в dev — допустимо). Перед ИБ-аудитом: env/user-secrets/внешний провайдер; не коммитить
  боевые пароли; добавить warning в README (T4).
- Сам файл `src/OneSTools.Ras.Exporter/appsettings.json` содержит dev-пароль `clickhouse`
  и uuid стендового кластера — на текущий момент не коммитится (решение пользователя).

### R5. `GetDatabaseName`: интернационализация имён БД
- Кластер с русским именем → `ras_cluster_Локальный кластер` (буквы кириллицы проходят
  `IsLetterOrDigit`, пробелы → `_`). ClickHouse такое выдерживает, но это ломает конвенцию
  `[a-z0-9_]` и усложняет миграции/GRANT.
- **Рекомендация: слаглификация (транслит/ASCII-fold) либо дефолт `{ClusterId}` при не-ASCII имени.**

### R6. Дублирование 5 коллекторов (шаблонный код)
- Session/Process/Connection/Lock — одна форма с разными типами; расходятся только запрос и
  конверт в MetricItem. После T1 правок catch-блок пришлось патчить 4 раза — сигнал дублирования.
- **Рекомендация (не срочно): базовый `PeriodicCollectorBase<TItem,TModel>` с делегатами
  poll/enqueue** — сократит поверхность будущих правок. Осторожно: не трогать семантику
  IsClosed-rethrow.

### R7. Публичная поверхность клиента
- `RasConnection`/`RasEndpoint`/все Message/Model типы — public (нужны тестам/LoadSim/будущим
  пользователям). Приемлемо для библиотеки-клиента; при публичной релизе — продумать
  стабильный API (сейчас это «внутренний» порт, публичный контракт не зафиксирован).

### R8. Сборщик мусора/аллокации в горячем пути
- Горячий путь (codec) уже span-based; транспортные пересылки аллоцируют
  `ArrayBufferWriter`+`ToArray` на каждый кадр (не критично при 1-5 опроса/с на кластер).
  При росте частот опросов — рассмотреть пулинг фреймов. Не блокер.

## 3. Прочие наблюдения (информационно)
- `ClusterMetricsWorker` инициализирует схему ClickHouse при каждом (пере)подключении —
  идемпотентно (`CREATE ... IF NOT EXISTS`), но лишние RTT; можно кэшировать «схема готова»
  по имени БД.
- `MetricsBatchingPipeline.DisposeAsync` останавливает батчеры последовательно; при
  недоступном ClickHouse остановка доходит до 2×5s grace × 5 типов ≈ 50s (T5-дефолты) —
  для shutdown grace хоста (30s) великовато; на проде учитывать в `ShutdownTimeout`.
- Mock-сервер: эхо-фолбэк удалён (T1-находка), отказы теперь как у реального RAS; дальше
  развивать мок по мере расширения API (GAP proto-контрактов: 36).
- Тесты real-стенда (17) при недоступном сервере скипаются — CI без стенда зелёный.
- LoadSim/MockServer не ссылаются на боевые секреты ✓.

## 4. Итоговый вердикт

Архитектура соответствует духу ориентира (host/options/pipeline/storage/DI/worker), допустимое
сознательное отклонение — батчинг (R1). Критичных структурных проблем нет; к закрытию предлагаются
R2 (healthchecks), R3 (backoff), R5 (имена БД) — по одному небольшому PR каждый. R4 — чек-листом
перед ИБ-аудитом (отдельный пункт плана).

## 5. Состояние после последующих исправлений (2026-09-25)

- R2: `RasExporterHealthCheck` отслеживает состояние соединений, отдельные опросы и число
  отброшенных элементов. Публикация — в лог по изменению статуса/описания.
- R3: экспоненциальный `BackoffPolicy` с jitter применяется при переподключении и
  повторной инициализации схемы. Сбор начинается после успешного создания схемы.
- R4: пароль ClickHouse убран из `appsettings.json`; devcontainer получает его из
  `CLICKHOUSE_PASSWORD`, порты хоста привязаны к loopback.
- R5: имена БД нормализуются `ClickHouseDatabaseNamer`; для гарантированной уникальности
  между кластерами в `DatabaseTemplate` следует включать `{ClusterId}`.
- Батчинг остаётся best effort: после исчерпания повторов данные теряются с записью в лог
  и health-check; при частичном сбое успешные группы не отправляются повторно.
- Клиент проверяет тип типизированного ответа; `GetSessionLocksRequest` включает три UUID
  в порядке `clusterId`, `infobaseId`, `sessionId` (контракт v8platform/protos).
